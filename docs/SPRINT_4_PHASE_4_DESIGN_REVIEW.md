## 1. What Phase 4 is, and what it deliberately is not

**QA answers a different question than Refinement.** Phase 3's `design-refinement-service.ts` asks *"make it better"* — it takes a generated wireframe and Design Memory and produces concrete typography/spacing/layout/motion/mobile values, validated against `lib/design-intelligence/`'s own rules by construction. Phase 4's `design-qa-service.ts` (still unbuilt) asks a categorically different question: *"is this ready for a founder to confidently present to a prospective client?"* — a judgment made **after** Refinement has already done its job, not a repeat of it. Per `docs/ARCHITECTURE_SPECIFICATION_V1.md` §2's own explicit principle: **"QA validates and reports differences but never redesigns."** A QA finding is a report, not a fix — this is the single hardest boundary this document has to keep clean, because it is the easiest one to blur by accident (a QA check that "helpfully" adjusts a spacing value on failure has quietly become Refinement wearing a QA badge).

**Desired pipeline placement**, per the founder's directive and consistent with `docs/ARCHITECTURE_SPECIFICATION_V1.md` §1's canonical shape:

```
Business Analysis → Design Brief → Reference Selection → Generation → Design Refinement → Design QA → Founder Review
```

Concretely, against what exists today: `design-brief-service.ts` (researching) → founder approves (reviewing → designing) → `design-generation-service.ts` (`generateWireframe`/`assembleComponents`) → `design-refinement-service.ts::refineDesign()` (already wired into `runDesignGeneration()`, Phase 3) → **Design QA (Phase 4, this document)** → the `designing → qa` transition → founder review. QA is the last automated gate before a human ever sees the output, mirroring Sprint 3's `analysis-service.ts` → `insight-service.ts` → `opportunity-scoring-service.ts` → `opportunity-report-service.ts` → UI shape (`docs/ARCHITECTURE_DECISIONS.md` ADR-011): each layer does one job, QA's job is grading, not producing.

## 2. QA Philosophy — Evidence First, extended to visual/creative output

Continues, rather than reinvents, the standard Sprint 3 set for the Opportunity Report (ADR-013) and Phase 1–3 already held `lib/design-intelligence/`'s validators to: **use deterministic evidence wherever a quality judgment can actually be measured, and reach for an AI-derived judgment only where deterministic measurement is genuinely insufficient.**

**The rule that governs every category below:** a deterministic check and an AI-derived judgment must never be blended into one number or one grade that reads as objective. Every AI-derived assessment in this document's design **must be explicitly labeled "AI-derived assessment"** in whatever it produces — never presented as if it were a measurement. This is not a stylistic preference; it's the same failure mode ADR-013 exists to prevent (a confident-sounding score standing in for a measurement that didn't happen), applied to a domain — visual/creative quality — where the temptation to let a model's confident-sounding output pass as fact is structurally higher than it ever was for the Opportunity Report's numeric measurements.

**What "deterministic" means concretely in this codebase already:** a check is deterministic if it's a pure function over structured data or measured values — exactly what `lib/design-intelligence/`'s validators (`validateTypeScaleOrdering`, `validateSpacingScale`, `matchesGenericSaasTemplate`, `validateMotionChoice`, `validateTouchTarget`, `validateMobileTypeChoice`, `findDuplicateSectionStructures`) already are, and exactly what `accessibility-adapter.ts`'s axe-core violations and `lighthouse-adapter.ts`'s category scores already are for the Analysis Engine's own domain. **What "AI-derived" means:** a judgment that requires interpreting content, composition, or intent in a way no deterministic rule can fully capture — "does this look bespoke for this business," "does the tone match a law firm's register" — the same category of judgment `design-intelligence-service.ts` already makes for creative direction, now applied to *evaluating* rather than *producing* a design.

## 3. The central architectural fact this document has to name honestly: there is no renderer yet

Before the category-by-category breakdown, one finding shapes nearly every category below and has to be stated plainly rather than discovered piecemeal in §5: **nothing in this codebase today produces an actual rendered page.** `design-generation-service.ts` produces a `Wireframe` (an ordered list of `WireframeSection`s) and a `ComponentNode` tree (component kind + named slots, each tagged `source: "real" | "placeholder"`). `design-refinement-service.ts` produces a `RefinedDesign` — concrete typography scale values, spacing values, a grid, motion timings, touch-target sizes — all still structured JSON. **At no point does any of this become HTML, CSS, or a URL a browser could load.** `docs/ARCHITECTURE_SPECIFICATION_V1.md` §1's pipeline names a terminal "Finished Website" artifact and a "Generation Engine" distinct from Design Intelligence; what's actually built under that name today is a deterministic *specification* assembler, not a page renderer.

This matters immediately and concretely: `accessibility-adapter.ts` and `lighthouse-adapter.ts` (Sprint 3's real, working, puppeteer/axe-core/Lighthouse infrastructure) are both **pure functions of a URL** — `runAccessibilityAdapter(targetUrl)`, `runLighthouseAdapter(targetUrl)`. They cannot run against a `Wireframe`/`ComponentNode`/`RefinedDesign` JSON object; there is nothing to point headless Chrome at. Any QA category that needs an actually-rendered page — real contrast measurement, real Lighthouse performance/accessibility/SEO scores, a genuine 375px-viewport screenshot, real DOM-based touch-target measurement — is **blocked on a rendering capability that does not exist and that this planning pass is not authorized to build** (building a renderer would itself be "more generation," which the founder's directive explicitly says Phase 4 is not).

**This is named here as the unavoidable dependency the founder's directive asked to be called out explicitly, not silently worked around.** It is not this document's place to decide whether that renderer gets built, when, or by whom — only to be honest that §5's Mobile, Accessibility, and Performance QA categories, and part of Layout QA, cannot reach "real measurement" without it, and that Phase 4 as scoped by this document can only build the *structured-data* half of QA now. The architecture below is designed so that gap is a clean seam, not a blocker to defining the rest: every category is split into what's checkable today against JSON and what becomes checkable once (if) a rendering step exists, so nothing downstream has to be redesigned when that capability eventually arrives — the same "build the seam, not the heavy infrastructure behind it" judgment `docs/SPRINT_4_ARCHITECTURE_RECOMMENDATION.md` §1 already made once for Design Intelligence.

## 4. QA categories

Each category states: what's deterministic and checkable **today** (structured data), what would become deterministic **once a renderer exists**, and what stays AI-derived regardless. Every deterministic check named as "existing" below is a real function already in this codebase, not a proposed one — reuse, not duplication, per the founder's explicit instruction to determine what can be reused before proposing anything new.

### 4.1 Typography QA
- **Deterministic, today:** `refineTypography()`'s output (`TypographyRefinement`) already carries a `violations: string[]` from `validateTypeScaleOrdering()` (hierarchy/scale ordering) and `validateTypographyChoice()` (family count ≤ `MAX_TYPE_FAMILIES`, line length/height within `READABILITY`'s band). QA's job here is not re-deriving these — it's reading Refinement's own violations and grading on whether any exist, plus a batch-level check Refinement doesn't do: is the chosen pairing (heading/body family names) actually distinct from other recent missions' pairings, or is one pairing quietly becoming the de facto default (§4's Never Generate concern, extended to typography).
- **Deterministic, once rendered:** computed line length/leading against actual rendered column widths rather than the `bodyLineLengthChars` value Refinement assumed; real font-loading/fallback verification.
- **AI-derived:** whether the pairing is a *deliberate* choice for this business's register (a serif/sans pairing that reads "law firm" vs. one that reads "generic corporate") — Refinement's rules check structural validity, not whether the choice fits the brief's stated positioning. Must be labeled "AI-derived assessment."

### 4.2 Spacing QA
- **Deterministic, today:** `refineSpacing()`'s `violations` from `validateSpacingScale()` (scale has enough steps, is monotonic); `SectionSpacingValue`'s role-proportional check (hero > content > closing, per the existing `SECTION_PADDING_STEP_INDEX_BY_ROLE` table) is itself re-derivable as a QA check — verify every section's assigned padding step is consistent with its `spacingRoleFor()` role, catching a Refinement regression rather than trusting Refinement's own output blindly (the same "defense in depth, re-verify independently" pattern `refineLayout()` already applies to `matchesGenericSaasTemplate`).
- **Deterministic, once rendered:** actual computed spacing between rendered DOM elements, catching a value that was correct in the spec but lost in whatever eventually translates spec → markup.
- **AI-derived:** "does this read as crowded or as empty" at a holistic, whole-page level — a scale can pass every numeric check and still read as visually unbalanced in aggregate. Must be labeled "AI-derived assessment."

### 4.3 Layout QA
- **Deterministic, today:** `refineLayout()`'s `matchesGenericTemplate` and `leadsWithHero` are re-checkable independently at QA time (defense in depth beyond Refinement's own self-check); `findDuplicateSectionStructures()` (`lib/design-intelligence/layout-rules.ts`) is **already built, already tested, and has no caller yet** — this is precisely the batch-level, cross-mission check `docs/SPRINT_4_DESIGN_REVIEW.md` §12 acceptance criterion 3 proposed and `design-refinement-service.ts`'s own header comment explicitly deferred to "design-qa-service.ts (Phase 4, not yet built)." QA is the correct, and only sensible, home for this function's first real caller.
- **Deterministic, once rendered:** actual grid-column alignment verification against `DEFAULT_GRID_RHYTHM`; measurable whitespace-balance metrics (e.g., ratio of content bounding-box area to viewport area per section).
- **AI-derived:** composition quality proper — visual balance, whether the sequencing genuinely follows this business's story (§5 of `docs/DESIGN_INTELLIGENCE.md`) rather than merely avoiding the one named banned pattern, whether the page reads as "composed" vs. "assembled." The goal, per the founder's directive, is **detecting weak/generic composition, not enforcing one correct layout** — the deterministic checks catch the worst, nameable offenses (the exact banned SaaS order, an exact duplicate structure); everything upstream of "not the worst case" is a judgment call and must be labeled as one.

### 4.4 Motion QA
- **Deterministic, today:** `refineMotion()`'s `violations` from `validateMotionChoice()` (duration inside `MOTION_DURATION_BAND_MS` unless `deliberateDeviation: true`, easing in `ALLOWED_EASING`, never a `BANNED_EASING_KEYWORDS` match) are directly re-checkable; a QA-level addition Refinement doesn't currently make explicit: verify every section marked `deliberateDeviation: true` actually has a stated reason traceable to the Design Brief's direction (today `motionIntensity` is brief-level, not per-section, so this reduces to "if any section deviates, the brief's own direction must justify `energetic`" — a cheap, real check).
- **Deterministic, once rendered:** actual measured animation timing and no-motion-on-`prefers-reduced-motion` verification (an accessibility-adjacent check this document hasn't seen named anywhere yet in this codebase and flags here as a real gap for whoever eventually builds the renderer, not something to quietly skip).
- **AI-derived:** "does this motion feel purposeful or performative" in aggregate across a full page — the qualitative half of §6's standard that a per-section duration/easing check cannot fully capture on its own.

### 4.5 Mobile QA
- **Deterministic, today:** `refineMobile()`'s `violations` from `validateTouchTarget()` and `validateMobileTypeChoice()` are re-checkable; `singleColumnVerified` is currently `true` by construction (the data model has no way to express a multi-column section) — QA should carry this flag through honestly as **"true by data-model construction, not independently verified,"** not silently upgrade it to a confident-sounding pass, per this document's own confidence discipline (§6).
- **Deterministic, once rendered — and this is the category where the §3 gap bites hardest:** the founder's directive names **375px as an explicit minimum validation viewport and an explicit acceptance criterion**, matching `docs/DESIGN_INTELLIGENCE.md` §12's own standard ("this category cannot pass on assumption, only on an actual rendered check"). This document adopts that as the Phase 4 standard **on record now**, explicitly not satisfiable today: a real 375px-viewport render, screenshot, and interaction check (nav collapse, section order at mobile width, touch-target hit-testing, overflow/cut-off content, CTA usability) is Mobile QA's actual pass condition, and until a renderer exists, Mobile QA's rendered sub-checks can only report `unavailable` (§6), never a false pass.
- **AI-derived:** does the mobile experience feel considered rather than a compressed desktop layout — requires an actual screenshot to judge at all, so this is doubly blocked by §3's gap, not just structurally deferred.

### 4.6 Accessibility QA
- **What already exists and should be reused, not duplicated:** `accessibility-adapter.ts` (real axe-core via headless Chrome) already measures exactly this category — but for the **target business's original site**, as part of the Analysis Engine (`docs/DESIGN_INTELLIGENCE.md` §12 already draws this distinction explicitly: "distinct from the target business's original site's accessibility, which is what the Analysis Engine's accessibility adapter measures"). The adapter itself is fully reusable *as infrastructure* — same function, same signature, same `AccessibilityRawResult` shape — the moment there's a second URL (the generated site's rendered preview) to point it at. No new accessibility-checking code needs to be written; a new caller does.
- **Deterministic, today (JSON-only, partial):** `accessibilityTargets` is a free-text field on `DesignMemory` (the LLM's stated intention, e.g. "AA contrast throughout") — QA can check this field is non-empty and flag it as a *stated intention*, explicitly not a *verified outcome*, until rendered.
- **Deterministic, once rendered:** the real thing — `runAccessibilityAdapter()` against the generated preview, graded against the same `violationCountByImpact` shape Sprint 3 already established, with the same "no CRITICAL/`critical`-impact violation" bar `docs/DESIGN_INTELLIGENCE.md` §12 already proposes.
- **AI-derived:** none, genuinely — accessibility is one of the categories in this document that is *entirely* deterministic once rendered; there is no qualitative residue the way there is for Layout or Typography. Framing this honestly cuts the other way from most categories here: Accessibility QA's whole story is "blocked on rendering, not blocked on judgment."

### 4.7 Performance QA
- **What already exists and should be reused, not duplicated:** `lighthouse-adapter.ts` is the exact infrastructure this category needs — already built, already tested, already producing the four 0–100 category scores plus Core Web Vitals audits Sprint 3 uses for the target site. Per the founder's explicit instruction to reuse existing Lighthouse infrastructure rather than building a second system: **Performance QA is "call `runLighthouseAdapter()` against the generated preview's URL and grade the result," not a new measurement system.**
- **The comparison Sprint 3 already sets up for free:** `docs/DESIGN_INTELLIGENCE.md` §7 names the actual bar — "should not regress versus the original site's measured performance." Because Sprint 3's `website_analyses` already stores the original site's Lighthouse scores, Performance QA's grading can be relative (delta vs. the same business's own baseline), not just an absolute threshold — a materially stronger check than a fixed cutoff, and one that requires no new data, only a second adapter call and a subtraction.
- **Deterministic, once rendered:** entirely deterministic, same reasoning as Accessibility QA — this category has no meaningful qualitative residue either.
- **Blocked today for the same §3 reason:** no URL exists yet to run Lighthouse against.

### 4.8 Trust QA
- **The permanent rule, restated because it is the one category with zero tolerance, not just low tolerance:** NEVER FABRICATE TRUST. No invented testimonials, certifications, awards, reviews, counts, partnerships, guarantees, credentials, or claims. Use real evidence if it exists; omit the section if it doesn't; never substitute a plausible-sounding invention.
- **This is the category where this codebase already has the strongest possible structural head start.** `ComponentSlot.source: "real" | "placeholder"` (`design-generation-service.ts`) is not a QA convention proposed by this document — it is **already enforced at generation time**, by construction, for every slot `assembleComponents()` produces, and `docs/SPRINT_STATUS.md`'s own Phase 2 entry documents this explicitly ("several slots... are placeholder-only today... a disclosed real gap, never invented content"). Trust QA's deterministic check is almost entirely mechanical because of this: **walk every `ComponentNode` whose `componentKind` is `TrustSignalRow` or `TestimonialList` (or any future trust-bearing kind) and assert no slot tagged `"placeholder"` is ever rendered with fabricated text** — today that's trivially true, since a `"placeholder"` slot's `value` is always `null` by the existing type, so the real risk this check guards against is a **future regression** (a change to `assembleComponents()` that starts putting plausible-sounding text into a `"placeholder"` slot's `value`), not today's actual output. This should be treated as the highest-priority CRITICAL-tier check in the entire QA suite precisely because it's cheap to check and catastrophic to miss (§14 of `docs/DESIGN_INTELLIGENCE.md`'s framing: worse than no certification section at all).
- **What's real to cross-check against:** `crawl-adapter.ts`'s expanded fields (`certifications`, `licenses`, `testimonials`, `reviews`, per `docs/ARCHITECTURE_SPECIFICATION_V1.md` §6 and `docs/SPRINT_STATUS.md`'s Item 3 entry) — a real, structured source of truth Trust QA can diff a `"real"`-tagged slot's value against, catching a subtler failure mode than the placeholder check alone: a `"real"` slot whose *content* doesn't actually trace back to anything the crawl captured.
- **AI-derived:** none for the fabrication check itself — that must stay strictly deterministic, precisely because this is the one category where an AI-derived "this looks plausible enough" judgment is the exact failure mode being guarded against, not an acceptable substitute for it.

### 4.9 Conversion QA
- **Deterministic, today:** CTA presence is directly checkable from the `ComponentNode` tree — does the wireframe include a section with a primary-action slot (hero's CTA, contact's primary action, schedule's book button, per the existing `TOUCH_TARGET_NAME_BY_SECTION` naming already used in `refineMobile()`); is there exactly one primary CTA kind repeated with consistent emphasis rather than several competing ones. `DesignMemory.ctaHierarchy.primary`/`.secondary` are directly inspectable fields.
- **Deterministic, once rendered:** actual visual prominence (contrast, size, position) of the primary CTA versus everything else on the rendered page — "does a button exist" is checkable today; "is it actually the visually dominant action" is not, without rendering.
- **AI-derived:** whether the contact/booking path's actual friction (form field count, information asked for) is appropriate for *this* business's category — per §9 of `docs/DESIGN_INTELLIGENCE.md`, there's no single correct form shape across Restaurant/Law Firm/HVAC, so "is this the right amount of friction for this industry" is a judgment call informed by the Design Brief's industry bucket, not a fixed numeric threshold. The founder's own framing — evaluate whether the desired business action is *clear*, not just whether a button exists — is squarely in AI-derived territory for exactly this reason.

### 4.10 Brand/Business Fit QA
- **Deterministic, today, partial:** does the generated output actually differ, structurally, from another mission's output for a different industry bucket — this is `findDuplicateSectionStructures()` again, viewed from the brand-fit angle rather than the generic-template angle (§4.11); does `DesignMemory.brandPersonality`/`contentTone` get referenced anywhere in the assembled copy, or is it recorded but unused (a cheap "was this field actually load-bearing" check, distinct from judging whether the tone itself is *good*).
- **AI-derived, and this is the category that is honestly almost entirely AI-derived:** does the typographic mood, color direction, imagery style, and copy tone actually read as "restaurant" vs. "law firm" vs. "HVAC" — not merely "not identical to another mission" (§4.11's mechanical proxy) but genuinely *fitting* this business's industry, audience, services, location, and positioning as the Design Brief stated them. The founder's own bar — must not produce identical visual treatment across industries — is a necessary condition this document can check mechanically (§4.11), but not a sufficient one; two visibly different but equally generic treatments would both pass the mechanical check and both fail this category's actual intent. Labeled "AI-derived assessment" without exception.

### 4.11 Generic Template Detection
- **Deterministic, today, and already built:** `matchesGenericSaasTemplate()` (checked at generation time, re-checkable at QA time as defense in depth) and `findDuplicateSectionStructures()` (built, tested, unused — QA is its first real caller, §4.3) together cover the two most concrete, named signals from the founder's list: repetitive sections and generic hero structures reduce to the same section-order data these two functions already consume. `NEVER_GENERATE_RULES` (`lib/design-intelligence/never-generate-rules.ts`) already names the rest of the founder's list as structured data — excessive cards, unnecessary gradients, emoji icons, weak typography, stock/generic imagery, repeated patterns — each entry already paired with the positive standard it protects (per that module's own design). Per the founder's explicit instruction: **start with these explainable rules, not a speculative ML classifier.** Several of `NEVER_GENERATE_RULES`'s entries (emoji-as-icon, a random decorative gradient with no semantic role) are concretely checkable once there's rendered markup or even just a component-slot content scan; others (whether an illustration reads as "generic AI stock art") stay AI-derived regardless of rendering, the same honest split `docs/SPRINT_4_DESIGN_REVIEW.md` §7 already named for this exact concern ("harder to grade mechanically than 'does this string contain the word Lighthouse'").
- **AI-derived:** the residual, hardest-to-name cases the rule list doesn't yet cover — this is the one category `docs/DESIGN_INTELLIGENCE.md` §11 itself says should grow over time as real generated output surfaces new failure modes, not a fixed, complete list on day one.

## 5. Reference-driven design — does "references teach principles, not layouts to copy" belong in Phase 4 QA?

**Yes, and it's a natural extension of a boundary this codebase has already committed to twice, not a new idea being imported.** `docs/SPRINT_4_DESIGN_REVIEW.md` §8 names "reference-library-as-template-in-disguise" as **the highest-priority risk in that entire document**, and §10's citation requirement ("a reference informs the Design Brief's reasoning, and must never be the source of the actual section order, copy structure, or component tree that ships") already exists as a stated rule — what's missing is a QA-time check that actually verifies it held, rather than trusting the Design Brief's own citations to be honest about themselves. Concretely, this fits as a genuine Phase 4 addition (not previously scoped anywhere): cross-check the generated `Wireframe`'s section order and `ComponentNode` kinds against the specific reference(s) `DesignBrief.referencesConsidered` cited — if the generated structure matches a cited reference's structure more closely than it matches the citation's own stated *reasoning* (typographic mood, layout family, motion band — the semantic categories `lib/design-references/reference-library.ts` already tags references by, per `docs/SPRINT_4_DESIGN_REVIEW.md` §8's own proposed selection mechanism), that's a concrete, checkable instance of the risk materializing, not just a documented worry. This check is deterministic in structure (comparing two section-order lists, comparing tagged categories) even though *why* a match matters is a judgment this document inherited rather than invented. It should be added to §4.3 (Layout QA) and §4.10 (Brand/Business Fit QA) as a named sub-check in either category rather than a twelfth top-level category — it's a lens on structural/brand-fit quality, not a new kind of quality.

Genuine fit for Obsidian OS specifically, not a blind adoption: this reference-informs-never-structures principle already matches `docs/VISION_GUARDRAILS.md`'s "not a template marketplace" commitment and `docs/DESIGN_INTELLIGENCE.md` §1's "the founder isn't buying HTML, they're buying confidence" framing precisely — a design that's traceably derived from a reference's structure is the visual-domain version of a fabricated trust signal (§4.8): technically plausible-looking, but not actually earned for *this* business.

## 6. QA Scoring Model

**The one rule every other rule in this section serves: a Deterministic Score and an AI-Derived Assessment are never blended into one number that reads as objective.** This is §2's philosophy made concrete as a data shape.

**Category result, per category (§4's eleven):**
- **`deterministicScore`** — a value in `{PASS, MINOR, MODERATE, CRITICAL}` (the discrete scale `docs/DESIGN_INTELLIGENCE.md` §12 already establishes, matching Sprint 3's own precedent of a named grading scale over a raw number), computed **only** from the category's deterministic checks (§4's "deterministic, today" and "deterministic, once rendered" sub-lists). A category with zero deterministic checks runnable in the current environment (e.g., Accessibility or Performance QA before a renderer exists) does not get a fabricated `PASS` — it gets `unavailable` (below), the same discipline ADR-013 already established for the Opportunity Report's own confidence ratings ("no fake scores when data is unavailable").
- **`aiDerivedAssessment`** — present only for categories with a real AI-derived component (§4.1–§4.5, §4.9, §4.10, §4.11's residual cases; explicitly absent for §4.6/§4.7 where nothing AI-derived exists), structured as `{ label: "AI-derived assessment", grade: MINOR|MODERATE|CRITICAL|no-finding, reasoning: string, citedEvidence: string[] }` — `reasoning` and `citedEvidence` are mandatory, mirroring the Design Brief's own citation requirement (§10 of `docs/SPRINT_4_DESIGN_REVIEW.md`): an AI-derived grade with no stated reasoning is exactly the "confident-sounding score standing in for a judgment that didn't actually happen" failure this whole document exists to prevent.
- **`confidence`** — `High | Medium | Low | Unavailable`, the same four-value scale ADR-013 established for the Opportunity Report, reused rather than reinvented. `Unavailable` is not a low score — it's an honest statement that the check couldn't run (most categories, most of the time, until §3's renderer gap closes), and must render distinctly from a real `CRITICAL`, never conflated with one.
- **`evidence`** — the concrete artifact backing the score: which validator ran and what it returned for a deterministic check; which specific structured fields (citations, tagged references, component slots) the model was shown for an AI-derived one. Every category result must carry evidence or must carry `confidence: Unavailable` — no third option.

**Overall pass/fail threshold, per `docs/DESIGN_INTELLIGENCE.md` §12's own already-proposed rule, adopted here rather than re-litigated:** any category at `CRITICAL` (deterministic or AI-derived) blocks handoff to founder review. Trust QA (§4.8) is the one category with zero tolerance rather than low tolerance — any fabrication finding is automatically `CRITICAL` regardless of every other category's score, exactly as `docs/DESIGN_INTELLIGENCE.md` §12's table already states. A batch of all-`Unavailable` categories (the realistic state of this system the day Phase 4 ships, before a renderer exists) does **not** default to pass — it should read as "QA incomplete," a third state distinct from both pass and fail, forcing an honest founder-facing statement of what was and wasn't actually checked rather than a green checkmark earned by absence of failure.

## 7. QA Failure Handling — conceptual flow only, no loop implemented

**The flow, mirroring `docs/DESIGN_INTELLIGENCE.md` §12's already-stated shape:**

```
Generation → Refinement → QA
                            ├─ PASS (no CRITICAL) → Founder Review
                            └─ FAIL (any CRITICAL) → controlled refinement → QA again (capped)
```

**Should automated refinement-on-failure exist at all?** This document's judgment: **conceptually yes, for a narrow subset of CRITICAL findings, but this is exactly the piece `docs/ARCHITECTURE_SPECIFICATION_V1.md` §2's "QA never redesigns" principle constrains hardest**, and it must not be implemented as anything resembling an autonomous loop. The distinction worth drawing precisely: QA finding a `CRITICAL` on a **deterministic** check (a spacing scale that failed `validateSpacingScale`, a wireframe that slipped past `matchesGenericSaasTemplate`) is a case where re-running the *existing, already-deterministic* Refinement pass with the specific violation as input is plausible and safe — Refinement already owns "fix a rule violation," QA is only the thing that noticed one slipped through. QA finding a `CRITICAL` on an **AI-derived** judgment (Brand/Business Fit reads as generic, Layout reads as templated) has no obvious deterministic fix to trigger — "regenerate and hope" is not a controlled refinement step, it's an unbounded loop wearing a bounded loop's name, and this document explicitly does not propose that as Phase 4 scope.

**If proposed for a future phase, the design constraints that would have to hold, named now so they aren't skipped later:**
- **Max attempts:** a small, fixed, documented cap (`docs/SPRINT_4_ARCHITECTURE_RECOMMENDATION.md` §2 already recommended this be decided and enforced from the start, not retrofitted) — a specific small integer (2–3), not "until it passes."
- **Trigger:** only a `CRITICAL` on a category whose fix path is itself deterministic (§4.1–§4.5's rule-violation checks) may trigger an automatic re-refinement pass. A `CRITICAL` on Trust QA (§4.8), Accessibility QA, or any AI-derived-only category must **never** auto-trigger anything — it routes straight to a human, no exceptions, given Trust QA's zero-tolerance framing and Accessibility's real compliance stakes.
- **Loop termination:** cap reached with a still-`CRITICAL` result terminates the loop and routes to founder review **with the failure disclosed**, not silently retried indefinitely and not silently downgraded to pass.
- **Failure recording:** every QA run (pass or fail, automated retry or not) is a permanent record — per `CLAUDE.md`'s Mission Engine rules, this is Decision Memory territory (`logDecision()` already exists, unused since Sprint 2 per `docs/SPRINT_STATUS.md`'s Sprint 2 entry — a QA run is a legitimate, concrete future caller worth naming, not building here).

**Explicit statement per the founder's instruction:** uncontrolled AI iteration must be avoided. This document does not authorize an automated refinement loop of any shape — the above is a design sketch for a future phase's review, not a build plan, and the safest default until that future review happens is **QA failures always route to a human**, with automatic re-refinement treated as a possible later optimization for the narrowest, most deterministic failure class only.

## 8. Founder relationship — QA reduces workload, it does not replace judgment

Per ADR-000's non-negotiable commitment, restated for this stage specifically: **QA does not replace the founder's review — it exists to reduce what the founder has to catch manually.** The flow: AI prepares a candidate (Generation + Refinement) → QA verifies it against explicit, evidenced criteria → the founder reviews it, informed by QA's findings but not bound by them. A `PASS` from QA is not authorization to skip founder review — it's the same relationship the `qa` mission state already has to the founder-approval gate in `lib/workflow/mission-state.ts`: QA is a pre-filter that makes the founder's actual review faster and better-informed (a founder reviewing a design already knows "Typography: PASS, Trust: PASS, Layout: AI-derived MODERATE — reads slightly generic in the hero" walks in with a head start a founder reviewing raw, ungraded output doesn't have), never a replacement for the review itself. This mirrors Sprint 3's own precedent precisely: the Opportunity Report's confidence ratings didn't remove the founder from reviewing missions, they made each review faster and more targeted.

## 9. Five-Industry Validation Standard — methodology for the next real validation cycle

**Not executed by this document — this is a methodology to run later, once `design-qa-service.ts` actually exists**, per the founder's explicit instruction. Real validation, no mocked businesses, matching every prior Sprint 3/4 validation precedent (Katz's Delicatessen, Veslo Family Restaurant — both real, live, unaffiliated sites, per `docs/SPRINT_STATUS.md`).

**Coverage: Restaurant, Dentist, Law Firm, HVAC, Landscaping** — five real, live, independently-selected businesses, one per industry bucket already named in `docs/DESIGN_INTELLIGENCE.md` §10 and `lib/design-references/reference-library.ts`'s 16-entry set. For each business, the validation record should capture:

| Field | What it records |
|---|---|
| **Representative business** | Real business name, URL, industry bucket resolved by `resolveIndustryBucket()`. |
| **Design brief** | The actual `DesignBrief` produced — positioning, direction, citations — same as `docs/SPRINT_STATUS.md`'s existing Katz's/Veslo entries already record. |

Running against five simultaneously (or as close to simultaneously as practical) also makes `findDuplicateSectionStructures()` meaningful for the first time — Sprint 3/4's validations to date have never had more than two missions to compare against each other.

## 10. Acceptance Threshold — proposed Phase 4 definition of done

**The system does not pass Phase 4 because it builds, because tests pass, because JSON validates, or because a design exists.** Those are necessary preconditions for evaluating Phase 4 at all, not the definition of done — the same distinction `docs/SPRINT_3_REVIEW.md` and every phase report since has held itself to (green tests are a floor, not a finish line). **The real question, restated as the actual acceptance bar:** *would a founder confidently put their own name and logo on this generated website and present it to a prospective client?*

**Proposed, concrete Phase 4 definition of done, consistent with this document's own architecture:**

1. `design-qa-service.ts` exists, is called at the `designing → qa` boundary (per §1's pipeline placement), and produces a structured QA result covering all eleven §4 categories, in the scoring shape §6 defines — every category reads `PASS`/`MINOR`/`MODERATE`/`CRITICAL`/`Unavailable`, never silently omitted.
2. Every deterministic check named "already built" in §4 (typography/spacing/motion/mobile validators, `matchesGenericSaasTemplate`, `findDuplicateSectionStructures`, the Trust QA placeholder-slot audit) is actually wired as a QA-time check, not left as Refinement-only self-verification — QA's whole value proposition is independent re-verification, per §4.2's and §4.3's "defense in depth" framing.
3. Trust QA (§4.8) is implemented and enforced as the zero-tolerance category it's specified to be — this is non-negotiable given §14 of `docs/DESIGN_INTELLIGENCE.md`'s own framing of fabricated trust as this system's single most damaging possible output.
4. Every AI-derived assessment produced carries mandatory reasoning and citation, and is rendered/labeled distinctly from deterministic scores wherever the QA result is displayed — §6's core rule, checkable by inspecting the actual data shape, not just narratively true.
5. The renderer gap (§3) is disclosed, not hidden — any category that cannot run its rendered sub-checks reports `Unavailable` honestly rather than a fabricated `PASS`, and the overall QA result states plainly which categories were and weren't actually verifiable in the current environment.
6. At least one real end-to-end QA run against a real generated design (reusing Katz's Delicatessen or Veslo Family Restaurant's existing pipeline output, consistent with every prior phase's real-validation standard) is performed and recorded before Phase 4 is called closed — the Five-Industry benchmark (§9) is the *next* validation cycle, not a Phase 4 completion requirement itself, but *some* real run against real data is, per `CLAUDE.md`'s testing standard that nothing is complete until verified against something real.
7. `docs/DESIGN_INTELLIGENCE.md` §12's acceptance criteria are re-examined against what actually got built and updated if reality diverged from what that section proposed before any code existed — the same "docs describe implemented code, never future promises as if done" discipline this codebase holds itself to everywhere else.

**What Phase 4 completion explicitly does not require:** a rendering/deployment capability (§3 — named as a real, unavoidable dependency for full rendered QA, but not something this planning pass authorizes building, and therefore not something Phase 4's own completion can be gated on); an automated refinement loop (§7 — explicitly designed conceptually, not implemented); the Five-Industry benchmark actually executed (§9 — a methodology for the *next* cycle); an AI Creative Director or visual-reasoning capability (`docs/DESIGN_INTELLIGENCE.md` §13, explicitly long-term and out of scope here too).

## 12. Answers to the fourteen architecture questions

1. **Should QA operate on structured data, rendered pages, or both?** Both, by design — but only structured-data QA is buildable today (§3). The architecture (§4, §6) is deliberately shaped so rendered checks slot into the same category/scoring structure once a renderer exists, rather than requiring a redesign then.
2. **Which checks are deterministic?** Every check listed "deterministic, today" or "deterministic, once rendered" across §4.1–§4.11 — the large majority of them already exist as real, tested functions in `lib/design-intelligence/` and `lib/adapters/`, not proposed new code.
3. **Which require AI interpretation?** The qualitative residue named per-category in §4 — heaviest in Brand/Business Fit QA (§4.10, almost entirely AI-derived) and Executive Presentation-adjacent judgment inside Layout QA (§4.3); essentially absent in Accessibility QA and Performance QA (§4.6, §4.7), which are deterministic once rendered and have no qualitative residue at all.
4. **How is AI-derived confidence represented?** §6's `aiDerivedAssessment` shape — mandatory `label: "AI-derived assessment"`, `reasoning`, `citedEvidence`, and a `confidence` value from the same four-value scale ADR-013 established, never merged into the deterministic score.
5. **Are screenshots required for visual QA?** For the categories §3 and §4.5 name as rendering-dependent (Mobile QA's actual acceptance condition, Accessibility QA and Performance QA's real measurement, Layout QA's visual-balance sub-checks), yes — and none of them can be honestly satisfied without one, which is exactly why §3 names this as an unavoidable dependency rather than a nice-to-have.
6. **Should QA reuse existing adapters?** Yes, directly and without modification: `runAccessibilityAdapter()` and `runLighthouseAdapter()` (§4.6, §4.7) are ready to be called against a second URL the moment one exists; `lib/design-intelligence/`'s validators are ready to be called at QA time today, with zero new validator code required.
7. **Should QA produce evidence records?** Yes — §6 makes evidence a required field of every category result, not optional metadata; a result with no evidence must carry `confidence: Unavailable`, never a scored grade with nothing backing it.
8. **Should failed QA trigger automatic refinement?** Conceptually, for a narrow deterministic-failure subset only (§7) — not implemented, not authorized here, and explicitly never for Trust QA or any AI-derived-only category.
9. **What's the max refinement loop?** Not decided by this document — §7 states the constraint (small, fixed, documented, decided before any loop code exists) without picking the number, consistent with this being design-only.
10. **What stops the loop?** The cap itself, plus routing to a human on any AI-derived or Trust QA `CRITICAL` regardless of cap (§7) — no loop this document describes is allowed to run indefinitely or resolve itself without a human path.
11. **How does QA interact with Founder Approval?** QA runs at `designing → qa`, before founder review, as a pre-filter that informs but never replaces the founder's own judgment (§8) — mirroring the existing Founder Approval Gate's relationship to the Design Brief exactly.
12. **How is QA history stored?** Not designed in detail here (no migration proposed, per scope) — named as a natural `logDecision()`/Decision Memory consumer (§7), the same permanent-history pattern every other founder-facing decision in this codebase already uses, left for the implementation phase to design concretely.
13. **How should the five-industry benchmark be executed?** Per §9's methodology — five real, live, independently-selected businesses (Restaurant, Dentist, Law Firm, HVAC, Landscaping), full pipeline run per business, findings recorded in the table shape §9 defines, executed only once `design-qa-service.ts` exists.
14. **What constitutes Phase 4 completion?** §10's seven-point definition of done — a working, honestly-scored QA service covering all eleven categories with the deterministic/AI-derived split enforced in its data shape, not a specific numeric benchmark result or a fully rendered QA suite (which §3's dependency gap makes impossible to require honestly today).
