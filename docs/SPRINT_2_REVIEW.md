## Executive Summary

**What was built.** Sprint 1 shipped a working but architecturally naive foundation: a Next.js 14 App Router app with Supabase Auth, a `missions` table with two overlapping lifecycle fields (`status` and `stage`), owner-scoped row-level security, and a Mission Control dashboard. Sprint 2 was explicitly scoped as **infrastructure and documentation only** — no discovery, no lead generation, no email sending — on the premise that this is the foundation every later feature depends on, and that a scalable design paid for now is cheaper than a retrofit paid for later. Five things were built: (1) a single canonical `state` field replacing the two-field `status`/`stage` design that could silently drift out of sync; (2) multi-tenancy groundwork (`organizations`, `organization_members`, org-scoped row-level security everywhere) built well before there's any team/billing UI to need it; (3) a formal, typed event bus that is now the single writer for the mission timeline, designed as a swappable port/adapter so Sprint 3's agents can plug in without rework; (4) a Decision Memory schema and logging service, architecture-only, meant to start capturing training data the moment a real Approval Queue exists; (5) a Memory Vault (`companies` table) that's the anchor of the future CRM, with real (if minimal) write wiring so it starts accumulating data immediately rather than shipping as a dead table.

**What changed from the original plan.** Two things worth flagging plainly. First, the original Sprint 1 roadmap predicted Sprint 2 would be the Discovery Engine and Opportunity Scoring — instead, Sprint 2 became infrastructure, and that agent work was deliberately pushed to Sprint 3. This is a sequencing correction, not a scope cut: building the event bus and state machine before the agents that publish to them is the right order, and it was called out explicitly in `docs/11-Product-Roadmap.md` rather than left as a silent surprise. Second, during this review's independent build verification (see Build Validation below), a real production-build failure was found and fixed that neither of the two build sessions that produced Sprint 2's code and docs had caught — the fix and how it was missed are both described in full, because a review gate that only reports clean results isn't doing its job.

**Overall assessment.** The state machine, event bus, and RLS design are solid, deliberate, and well-justified — see the ADR log for the reasoning behind each. The two Sprint-2-native tables meant to accumulate long-term data (`decisions`, `companies`) are correctly schema'd but almost entirely unpopulated in practice: `decisions` has zero write paths anywhere in the codebase (no Approval Queue UI exists to call `logDecision()`), and `companies` has exactly one write path (mission creation), meaning most of its columns (`last_contacted_at`, `last_proposal_amount`, `follow_up_date`, `do_not_contact`) are schema with no code ever setting them. This is expected and was scoped that way deliberately, but a reviewer should not read "the Memory Vault is built" as "the Memory Vault has any real data flowing through it" — it has exactly the amount of data flowing through it that one `findOrCreateCompany()` call site produces, and nothing more. The Technical Debt section below is the honest, complete accounting of every shortcut, gap, and assumption; it is long on purpose.

## New Database Schema

Six migrations exist, applied in order: `0001_init.sql` (Sprint 1) through `0006_memory_vault.sql` (Sprint 2). Every table below is real, present in the migrations, and was re-read directly from the SQL files for this review — not summarized from memory of what was supposed to be built.

### `profiles` (0001, extended 0002)

One row per `auth.users` row, created automatically by the `handle_new_user()` trigger — never inserted by application code. Columns: `id` (PK, references `auth.users`), `email`, `full_name`, `avatar_url`, `default_organization_id` (added in 0002, references `organizations`), `created_at`, `updated_at` (maintained by a generic `set_updated_at` trigger). **Why it exists:** the natural place to hang per-user data that isn't auth-provider data, and the anchor for "which organization does this user act as by default," which every mission-creating code path needs. RLS: a user can only select/insert/update/delete their own profile row (`auth.uid() = id`) — this table was not moved to org-scoped RLS because a profile is fundamentally per-user, not per-organization, data.

### `organizations` (0002)

`id` (PK), `name`, `slug` (unique), `plan` (CHECK: `trial`, `starter`, `pro`, `agency`, `white_label`), `created_at`, `updated_at`. **Why it exists:** the tenant boundary for a future multi-tenant, white-label SaaS product, built now rather than retrofitted later (see ADR-004 for the full retrofit-cost argument). RLS: any org member can `select`; only `owner`/`admin` members can `update` (via the `is_org_admin()` helper below). There is deliberately no client-facing `insert` policy — the only way a row is created today is the `handle_new_user()` trigger, which runs as `SECURITY DEFINER` and is exempt from RLS. **Honest caveat:** the `plan` column exists but nothing in the codebase reads it or enforces any plan-based limit anywhere — it's schema for a feature (billing/plan entitlements) that doesn't exist yet, purely decorative today.

### `organization_members` (0002)

Composite PK `(organization_id, user_id)`, `role` (CHECK: `owner`, `admin`, `member`), `created_at`. Index on `user_id` (supports "which orgs is this user in" lookups). **Why it exists:** the membership join table that makes every other table's RLS possible. RLS: a member can select memberships in their own organizations; only owners/admins can manage (insert/update/delete) memberships. **Honest caveat:** there is no self-service "invite a teammate" flow — the only membership row created by any code path today is the one `handle_new_user()` creates for a brand-new user's own personal org. A second member can only be added by someone with direct database access. This is fine for Sprint 2 (no team UI is in scope) but should not be mistaken for "team invites work."

### RLS helper functions: `is_org_member(org_id)`, `is_org_admin(org_id)` (0002)

Both `SECURITY DEFINER`, `STABLE`, SQL functions checking `organization_members` for the calling user (`auth.uid()`). **Why they exist:** a naive RLS policy on `organization_members` that references `organization_members` in its own `USING` clause triggers Postgres's "infinite recursion detected in policy" error — the standard Supabase fix is a `SECURITY DEFINER` helper function that runs with the function-owner's implicit RLS exemption, breaking the cycle. Every membership-scoped policy from 0002 onward (missions, mission_events, decisions, companies) calls one of these two functions rather than re-implementing the check inline, which also means there is exactly one place to fix or extend the membership-check logic later.

### `missions` (0001, reshaped by 0003)

The mission's core table, and the one that changed the most in Sprint 2. Current columns: `id` (PK), `owner_id` (who created/is assigned to the mission — kept, but no longer the RLS boundary), `organization_id` (added 0003, `NOT NULL`, the RLS boundary now), `business_name`, `website_url`, `state` (text, `NOT NULL`, 11-value CHECK constraint — see Mission Engine section below), `state_changed_at` (`NOT NULL`, maintained by a dedicated trigger, independent of `updated_at`), `company_id` (added 0006, nullable, links to the Memory Vault), `created_at`, `updated_at`. Indexes: `organization_id`, `state`, `company_id`. **What changed and why:** Sprint 1 had two overlapping fields, `status` and `stage`, that could drift out of sync with nothing enforcing their correlation — 0003 collapsed them into one `state` field with a backfill migration (full mapping in the Mission Engine section). RLS: `is_org_member(organization_id)` for select/insert/update/delete, replacing Sprint 1's direct `owner_id = auth.uid()` checks.

### `mission_events` (0001, reshaped by 0004)

`id` (PK), `mission_id` (references `missions`), `organization_id` (added 0004, denormalized — see below), `event_type` (10-value CHECK constraint matching the event bus's `DomainEventType` catalog exactly), `message` (human-readable), `metadata` (jsonb), `actor` (added 0004, default `'system'`), `created_at`. Indexes: `organization_id`, plus the original `(mission_id, created_at)` composite from 0001. **Why `organization_id` is denormalized here** rather than requiring a join to `missions` on every check: `mission_events` is expected to become the highest-volume table in the schema (every agent publishing every piece of work, eventually many events per mission), and both RLS checks and future analytics queries ("every event across an organization") are simpler and faster against a direct column than a join-per-row. This is a real, acknowledged tradeoff — see ADR-007 and the Technical Debt section for the drift risk it accepts. **Honest caveat on `actor`:** the column exists and is documented as supporting `system`, `user`, or `agent:<name>` values, but the only code path that writes to this table (`SupabaseEventBus.persist()`) hardcodes `actor: "system"` unconditionally — nothing today ever writes `user` or `agent:<name>`, even though the schema was built to support it. This is a real gap, not just a forward-looking placeholder that's merely unused; it means the "who did this" question the column promises to answer cannot actually be answered from any current data.

### `decisions` (0005)

`id` (PK), `mission_id`, `organization_id` (denormalized, same rationale as `mission_events`), `created_at`, `decision_type` (11-value CHECK: `approve`, `reject`, `not_a_fit`, `edit_subject`, `edit_email`, `edit_proposal`, `change_price`, `skip_industry`, `approve_immediately`, `wait_until_later`, `archive`), `ai_recommendation` (text), `user_action` (text), `before_value`/`after_value` (jsonb, nullable), `industry`, `opportunity_score`, `website_score`, `proposal_price` (`numeric(10,2)`), `email_subject`, `email_length`, `website_theme`, `business_category`, `metadata` (jsonb catch-all). Indexes: `mission_id`, `organization_id`, `decision_type`. **Why `before_value`/`after_value`/`metadata` are `jsonb` rather than rigid typed columns:** the shape of "before" and "after" varies by `decision_type` (a string for an edited subject line, a structured object for an edited proposal, a number for a changed price), and nobody has built the recommendation/scoring system that will eventually consume this data yet — guessing its exact needs now risks a table of wrong-shaped columns needing a future migration. Named columns capture the handful of signals expected to matter regardless of that future system's shape (a score, a price, an industry); `jsonb` defers the rest. **Honest caveat, stated as plainly as possible: nothing in this codebase calls `decisionRepository.insert()` or `logDecision()` today.** Zero rows will ever land in this table until a future Approval Queue UI exists and calls it. The table, the types, and the service function all typecheck and are ready — but "ready to be called" and "being called" are different claims, and this document is making the first claim, not the second.

### `companies` (0006) — the Memory Vault

`id` (PK), `organization_id`, `business_name`, `website_url` (normalized — protocol and trailing slash stripped, lowercased — in the service layer, not SQL), `industry`, `business_category`, `first_discovered_at`, `last_mission_id` (references `missions`, `ON DELETE SET NULL`), `total_missions_count` (default 0), `last_contacted_at`, `last_proposal_amount`, `last_proposal_sent_at`, `follow_up_date`, `design_preferences` (jsonb, freeform), `do_not_contact` (boolean, default `false` — an explicit compliance/opt-out flag), `notes`, `created_at`, `updated_at`. Unique constraint on `(organization_id, website_url)`. Indexes: `organization_id`, `last_mission_id`. **Why it exists now, not deferred until a CRM UI needs it:** if `companies` were added only once outreach/CRM work begins, every mission created before that point would need fuzzy business-name/URL matching to backfill which company it belongs to — exactly the error-prone work the normalization logic already exists to avoid doing ad hoc. Building it now, wired into mission creation, means real history accumulates from day one. **Honest caveat, equally plain: only two fields on this table are ever written by any code path today** — `total_missions_count` and `last_mission_id`, both set by the one call to `findOrCreateCompany()` inside `createMission()`. `last_contacted_at`, `last_proposal_amount`, `last_proposal_sent_at`, `follow_up_date`, and `do_not_contact` are schema with zero write paths — they exist so a future outreach/proposal agent has somewhere to write without a migration, not because anything populates them today. `do_not_contact` in particular defaults to `false` for every company and is never set to `true` by any code path, meaning it currently provides no actual compliance protection — it's a promise the schema makes that the application does not yet keep.

### `missions.company_id` (0006)

Nullable FK from `missions` to `companies`, added because Sprint 1 missions predate the Memory Vault concept. New missions populate it via the `findOrCreateCompany()` call inside `createMission()`.

### RLS posture, summarized

Every table from 0002 onward uses the same pattern: `is_org_member(organization_id)` gates reads, and writes are gated the same way (organization-management actions on `organizations`/`organization_members` additionally require `is_org_admin()`). No table is reachable by an authenticated user outside their organization's membership. `profiles` is the one exception, correctly scoped to the individual user rather than an organization, because it's inherently per-user data.

## Mission Engine

This section is deliberately structured to separate **what's fully built** from **what's stubbed**, because the two can look identical from a distance (both compile, both have doc comments, both have types) and a reviewer needs to be able to tell them apart at a glance.

### State machine — fully built

A single `state` column (`lib/workflow/mission-state.ts`, `supabase/migrations/0003_mission_state_machine.sql`) replaces Sprint 1's two-field `status`/`stage` design. Eleven states: `discovered, analyzing, researching, designing, qa, proposal, email, approval, sent, archived, rejected`. The primary linear sequence is `discovered → analyzing → researching → designing → qa → proposal → email → approval → sent → archived`. Three non-sequential transitions are explicitly, individually allowed rather than gated behind a generic escape hatch: `rejected` is reachable from any non-terminal, non-`sent` state (rejection is a first-class outcome, not a flavor of archiving); `qa → designing` is a revise loop; `rejected → archived` is the only way out of rejection. Two invariants are hardcoded and **cannot** be overridden even by the workflow engine's own `allowNonSequential` escape hatch: `archived` never transitions to anything, and `rejected` only ever transitions to `archived`. `transitionMissionState()` (`lib/workflow/mission-workflow.ts`) is the single enforcement point for all of this — there is no other code path in the repository that writes `missions.state` directly. This is real, tested-by-typechecking (not unit-tested — see Technical Debt) logic, not a stub.

The old→new state mapping (the 0003 migration's backfill `CASE` expression) deserves restating here because it's the least obvious decision in the sprint: `stage = 'seo'`, `stage = 'performance'`, and `stage = 'deployment'` **all** fold into the new `qa` state. The reasoning: SEO checks, performance checks, and preparing a deployable preview build are all sub-activities of the quality-assurance gate, not distinct pipeline stops an operator needs to see as separate top-level states on a dashboard — the fine-grained detail of which check is running is exactly what the event bus is for. This is a genuine information-hiding tradeoff, made deliberately (see ADR-005), and it means Mission Control today cannot distinguish "running SEO checks" from "building a preview" without reading the event timeline — which doesn't have a UI yet either (see Mission Control gaps in the blueprint's §5).

### Event bus — fully built, with one explicitly limited property

`lib/events/` defines `DomainEvent`, a discriminated union covering ten event types (`MissionStarted, WebsiteScanned, SEOComplete, ProposalReady, EmailDraftReady, MissionApproved, MissionRejected, MissionArchived, StateChanged, DecisionLogged`), and `EventBus`, an interface with one implementation, `SupabaseEventBus`, which persists every published event to `mission_events` and additionally fans it out synchronously to any same-process subscribers. The mission workflow engine publishes through this bus exclusively — Sprint 1's direct `mission_events` inserts are gone. **This is genuinely built and working for the four event types the workflow engine itself publishes** (`MissionStarted` on mission creation, `StateChanged` on every transition, `MissionRejected`/`MissionArchived` on those specific actions). **It is not built for the five event types an actual AI agent would publish** (`WebsiteScanned, SEOComplete, ProposalReady, EmailDraftReady`, and `MissionApproved`) — those exist as typed shapes in `lib/events/types.ts` with **zero code anywhere that calls `publish()` with them**. A reviewer skimming the type catalog could reasonably assume these represent working integrations; they don't. They represent a contract Sprint 3's agents are expected to fulfill.

The explicitly limited property, stated in the code's own doc comment and worth repeating here because it matters for the Sprint 3 recommendation below: the in-process subscriber fan-out is **not durable and not cross-process**. It doesn't survive a server restart and doesn't fan out across server instances. This is fine today because nothing subscribes to it, but it is a real architectural gap that must be addressed — not worked around, addressed — before any agent runs as an independent background worker rather than inline in a request.

### Queues, retry, logging, failure handling — not built; do not exist

There is no job queue. There is no scheduler. There is no retry policy, anywhere, for anything. There is no background worker process of any kind. A mission created via `POST /api/missions` is inserted at `state: 'discovered'` and then **sits there indefinitely** — no code path in this repository advances it. If Sprint 3 adds a Discovery Agent, that agent still needs an entirely separate piece of infrastructure (a scheduler, a queue, a worker runtime) to actually be invoked, on some cadence, against some set of missions — none of which exists yet. "Failure handling" in the sense of retry-with-backoff, dead-letter handling, or partial-failure recovery does not exist because there is no agent execution to fail in the first place. The only "failure handling" that exists today is ordinary exception propagation: if `transitionMissionState()` throws (e.g., an invalid transition), the caller (an API route) catches it and returns a `500` — this is request-level error handling, not a resilience system for autonomous background work.

### Approval flow — schema exists, UI and wiring do not

The `decisions` table and `logDecision()` service exist and typecheck (see Database section above). No Approval Queue screen exists. No code path in the application calls `logDecision()`. The `approval` mission state exists in the state machine and can be reached by `transitionMissionState()`, but nothing in the UI lets a human see a mission in that state and act on it beyond seeing its state badge on the Mission Control list. The entire "human reviews a completed mission and approves/rejects/edits it" flow described in the product vision is, today, three unconnected pieces: a state a mission can be in, a table that would record the decision, and a state badge that shows the state — with no screen connecting them.

## Decision Memory

The intended data model, and how it's meant to feed a future Learning Engine (none of the "feeds a Learning Engine" part is built — this describes the relationship the schema is designed to support):

`organizations` is the tenant boundary everything else hangs off. Within an organization, `companies` (the Memory Vault) is the entity that persists across time — one row per real-world business, accumulating history across every mission that business is ever part of. `missions` is the unit of work — one attempt to move one company through the pipeline once; `missions.company_id` links a mission to its persistent company record, and `companies.last_mission_id`/`total_missions_count` let the company record summarize its mission history without needing to re-scan every mission each time. `mission_events` is the fine-grained, chronological log of everything that happened *during* a mission — every state transition, every future agent's output, timestamped and typed. `decisions` is the fine-grained log of every point a human *intervened* in a mission — not what the system did, but what the human did in response, paired with what the AI recommended (`ai_recommendation`) and the surrounding context at that moment (`opportunity_score`, `website_score`, `proposal_price`, `industry`, etc., captured on the decision row itself rather than requiring a join back to the mission's state at that point in time, which could have already changed by the time anyone queries it).

The intended future Learning Engine's training signal is exactly the `decisions` table: `ai_recommendation` vs. `user_action`, with `before_value`/`after_value` for edits, joined against the business/mission context columns captured on the same row. Because `organization_id` is on every table in this chain, the Learning Engine (whenever it's built) can be trained per-organization if agencies turn out to have meaningfully different judgment patterns, or pooled across organizations if they don't — that choice is deferred, not foreclosed, by this schema. **The honest limit of all of this:** it is a well-shaped, empty pipe. Every claim in this paragraph describes what the schema is *designed to support*, not what is *currently happening* — restated from the Database section, because it's the single most important caveat in this document and bears repeating in context: zero decisions have ever been logged, because nothing calls `logDecision()`.

## Multi-Tenancy

`organizations` and `organization_members` (0002) establish the tenant boundary. Every user gets a personal organization auto-provisioned at signup (`handle_new_user()`, rewritten in 0002 to do this atomically alongside profile creation) with themselves as `owner` — solo use today feels identical to Sprint 1's single-user model, with no extra signup steps, while every row created from Sprint 2 onward carries a real `organization_id`. `role` on `organization_members` supports `owner`, `admin`, `member`, though nothing in the application differentiates their permissions today beyond the two RLS helper functions (`is_org_admin()` currently gates only organization/membership management, not any mission- or company-level permission difference between an `admin` and a `member`).

**The future SaaS architecture this enables:** an organization is the unit a subscription plan, a billing relationship, a white-label brand, and a team all attach to. Because every data table (`missions`, `mission_events`, `decisions`, `companies`) is already organization-scoped, adding team management (invite flows, role-based UI permissions), billing (Stripe, tied to `organizations.plan`), and white-labeling (a custom domain/brand per organization) are all additive features on top of an existing tenant boundary, not schema migrations that touch every table's RLS policy again.

**Why this was built now instead of later — the argument, stated plainly, not just asserted:** retrofitting tenant isolation onto a schema and RLS policy set written assuming single-owner rows means rewriting every policy, backfilling an `organization_id` onto every table (a materially riskier migration once real customer data exists rather than zero rows), and auditing every existing query path for an implicit "this only returns my own rows" assumption that a tenant-scoped model breaks. Doing it now, while `missions` and `mission_events` are the only tables with any live-shaped data and before a single real customer exists, kept the migration low-risk, and every table built since (`decisions`, `companies`) was tenant-scoped from its first line rather than needing a follow-up migration of its own. The cost paid now, stated honestly: solo users carry an invisible "personal organization" they never see or manage, adding a small amount of indirection to every query (an `organization_id` lookup via `profiles.default_organization_id`, visible in `app/page.tsx` and `app/api/missions/route.ts`) for a benefit that has no UI yet and won't be exercised for several more sprints. This is a bet that the retrofit-avoidance is worth more than the current indirection cost — a reasonable bet at this stage, but a bet, not a certainty, and it's recorded as one in ADR-004 rather than presented as an obviously-correct choice.

## Technical Debt

This section is intentionally long. The point of a review gate is surfacing what's not solid, not reassuring anyone that everything is fine — undersell nothing.

**No queue, scheduler, or background worker exists at all.** Every mission created today sits at `discovered` forever. This is the single largest gap between the product vision and the current implementation, and it blocks essentially all of Sprint 3.

**The event bus's in-process subscriber fan-out is not durable and not cross-process**, by explicit design (see Mission Engine section) — acceptable today only because nothing subscribes to it. Any Sprint 3 agent running as a separate worker process needs a real transport (Supabase Realtime, or a queue like Inngest/Trigger.dev) behind the same `EventBus` interface before it can rely on this mechanism for anything that matters.

**No automated tests exist anywhere in this repository.** Flagged after Sprint 1, still true after Sprint 2. `lib/workflow/mission-workflow.ts`'s transition validation (`transitionMissionState`'s sequential-vs-`allowNonSequential` branching, the hard `archived`/`rejected` invariants) is pure, dependency-injected, and the single highest-value candidate for the first unit tests this project writes — and still has none.

**`createMission()` has no transactional integrity.** It performs four sequential, independently-awaited database operations (insert mission → find-or-create company → update mission with `company_id` → publish `MissionStarted` event) with no rollback on partial failure. If the third call fails, the result is an orphaned mission with no `company_id` and no seed event. If the fourth call fails, the mission and company are correctly linked but the mission's timeline never records that it started. The Supabase JS client does not support multi-statement client-side transactions; fixing this properly requires wrapping the sequence in a Postgres function (RPC) called atomically, which was not done.

**`findOrCreateCompany()` has a real time-of-check-to-time-of-use race condition.** Two concurrent mission-creation requests for the same new business (same `organization_id` + `website_url`, not yet in `companies`) can both pass the "does this company exist" check before either inserts, and the second insert will fail on the `(organization_id, website_url)` unique constraint with an unhandled error rather than gracefully re-fetching the row the first request just created. Low probability with a single operator clicking a button today; a real risk once multiple background agents or multiple organization members can trigger mission creation concurrently.

**`mission_events.actor` is hardcoded to `"system"` for every event, unconditionally**, despite the column and its documentation explicitly describing `user` and `agent:<name>` as valid values. The "who did this" question this column exists to answer cannot currently be answered from any real data — this needs to be threaded through from the actual caller (a route handler knows the authenticated user; a future agent runtime would know its own name) before it's meaningful.

**`companies.do_not_contact` provides no actual protection today.** It defaults to `false` for every company and is never set to `true` by any code path — it's a compliance promise the schema makes that the application does not yet keep. This must be wired to a real opt-out mechanism (and checked by any future outreach code) before any outreach feature ships, not treated as already handled because the column exists.

**Most of the Memory Vault's columns have zero write paths.** Restated from the Database section because it's easy to miss: only `total_missions_count` and `last_mission_id` are ever written. `last_contacted_at`, `last_proposal_amount`, `last_proposal_sent_at`, `follow_up_date` are pure schema.

**`decisions` has zero write paths.** Nothing calls `logDecision()` anywhere in the application. The table, service, and types are ready; nothing uses them yet.

**No pagination anywhere.** `missionRepository.listByOrganization()`, `missionEventRepository.listByMission()`, and `decisionRepository.listByMission()` all fetch unbounded result sets. Fine at current data volumes (effectively zero); a real problem at any meaningful scale, addressed further in the CTO Assessment's bottleneck analysis.

**`npm audit` reports 5 high-severity vulnerabilities in `next@14.2.35` and its bundled `postcss`** (full advisory list in Build Validation). Not previously surfaced in any Sprint 2 documentation. Upgrading to `next@16.x` is a breaking change requiring its own migration effort and was explicitly not attempted during this documentation-only review.

**Forcing the entire app dynamic (`export const dynamic = "force-dynamic"` in the root layout) — the very fix that made the production build pass — permanently disables all static rendering and edge caching for every route, including `/login`, which has no session-dependent content and could otherwise be served from a CDN edge with zero origin load.** This was the correct, minimal fix for a build-breaking bug found under time pressure during self-review; it was not the most scalable fix. A more surgical approach — keeping `/login` statically renderable and only forcing dynamic rendering on session-dependent routes — was not attempted. This is a real, self-inflicted piece of debt introduced by this sprint's own bug fix, not inherited from Sprint 1.

**RLS depends on a `SECURITY DEFINER` function call (`is_org_member()`/`is_org_admin()`) evaluated per row on every policy check**, rather than, for example, a membership claim embedded in the user's JWT. Correct and secure; not the cheapest possible approach at high query volume. See CTO Assessment.

**`organizations.plan` is decorative.** No code path anywhere reads it or enforces any limit based on it.

**The hand-written `database.types.ts` doc comment claims that running `supabase gen types typescript` against a live project and dropping the output in "should be a minimal diff."** This is optimistic: the real codegen output would not import `MissionState`/`DomainEventType`/`DecisionType` from application-level files the way the hand-written version does (a genuinely nice DRY property of the hand-written version, arguably better than what codegen produces) — reconciling the two will require more than a drop-in replacement. A minor documentation-accuracy issue, not a functional one, but exactly the kind of small inaccuracy that compounds if left uncorrected.

**Product framing inconsistency between docs and running UI, introduced during this very review.** ADR-010 (added during this review pass) refines the product framing to "Autonomous Client Acquisition Operating System" across `docs/MASTER_BLUEPRINT.md`, `docs/00-Executive-Summary.md`, and `docs/01-Product-Vision.md` — but `app/login/page.tsx` and `app/layout.tsx`'s metadata still display the older "AI Agency Operating System" tagline, left untouched because this review gate is documentation-only and no code changes are in scope. This is a known, named piece of drift between docs and product, not an oversight — but it exists, and the first code-touching sprint after this review should close it.

**Single squash-commit-per-sprint git convention.** Works for a single contributor/agent working sequentially; will not scale once more than one person or agent is committing to this repository concurrently, and no branching/PR convention has been established for that case yet.

**No accessibility audit has ever been run.** Inherited Radix primitive behavior (keyboard nav, focus management, ARIA roles) is presumed adequate but has not been independently verified.

**No rate limiting exists on `POST /api/missions`** or any other endpoint. Not a problem with one authenticated operator; would need addressing before any public-facing or higher-traffic surface exists.

## Sprint 3 Recommendation

**This is a recommendation only — nothing below has been implemented, and this review gate explicitly does not authorize starting it.**

The original Sprint 1 roadmap and Sprint 2's own `docs/11-Product-Roadmap.md` both point at the same next step, and this review doesn't find a reason to disagree: **the first real agents — Discovery, Qualification (Opportunity Scoring), and Research — wired into the Sprint 2 event bus for real**, meaning they call `EventBus.publish()` with genuine `WebsiteScanned`/`SEOComplete`-shaped payloads instead of those types existing only in `lib/events/types.ts` with nothing producing them.

**What Sprint 3 gets for free from Sprint 2's infrastructure:** a state machine that already has `discovered → analyzing → researching` as valid sequential transitions ready to drive a mission through; an event bus that already persists whatever an agent publishes to the mission timeline and can fan out to same-process subscribers; a `companies` table already resolving/creating a Memory Vault record per business, ready to receive real `industry`/`business_category`/`design_preferences` data instead of nulls; org-scoped RLS already isolating one agency's discovered leads from another's, which matters the moment more than one organization exists.

**What Sprint 3 requires that Sprint 2 explicitly does not provide, and must be built new:** (1) a job runner/scheduler of some kind — nothing today advances a mission past `discovered`, and this is a new piece of infrastructure, not a config flag; (2) real Anthropic API wiring — the key exists in `.env.example`, no code anywhere calls the API; (3) the actual discovery mechanism itself (some combination of search/scraping to find businesses with poor websites) and the actual scoring logic — both genuinely new problem domains this codebase has not touched; (4) a decision about where agent code runs (inline in a Next.js API route on a cron trigger, a separate worker process, a third-party job platform) that has direct consequences for whether the event bus's current in-process-only fan-out is sufficient or needs the durable-transport upgrade flagged in Technical Debt.

**Complexity and risk, honestly estimated:** the Discovery Agent (finding businesses with poor websites) is the highest-risk, highest-complexity piece — it depends on external data sources (search APIs, business directories, or scraping) that this project has made zero technical decisions about yet, and "poor website" as a qualifying signal needs its own definition before Qualification can score against it. Medium complexity, medium risk. The Opportunity Scoring / Qualification agent is lower complexity if it consumes the Discovery Agent's output plus an LLM call, but its output quality is only as good as Discovery's input, so it's risk-coupled to that first agent rather than independently risky. The Research Agent (competitor/review analysis) is comparable in complexity to Discovery — external data sources again, a genuinely new integration surface. The job runner/scheduler is, in some ways, the least glamorous and most architecturally consequential piece of Sprint 3: get it wrong (e.g., build something that only works inline in a request rather than as genuinely autonomous background work) and it constrains every agent after it. Recommend treating the scheduler as its own reviewed decision — an ADR of its own — before agent-specific work begins, rather than an implementation detail decided inside the Discovery Agent's own PR.

## CTO Assessment

*Written self-critically, against the project's own prior decisions, per the explicit instruction that produced this section — not a defense of Sprint 1 and 2's choices, an audit of them.*

**What architecture decisions made the platform better?** Collapsing `status`/`stage` into a single `state` field (ADR-005) is the clearest unambiguous improvement in this sprint — it eliminated an entire class of bug (two fields silently disagreeing) that Sprint 1 had already demonstrated was a real risk, not a hypothetical one, and the text+CHECK-constraint-over-native-enum choice was the right call for a state vocabulary that had already changed once in two sprints. Building multi-tenancy now (ADR-004) rather than later is very likely correct — the retrofit-cost argument is sound, and paying the cost while there's zero live data is objectively cheaper than paying it after there's real customer data to migrate carefully. The event bus as a port/adapter (ADR-006) rather than either "call Supabase directly everywhere" or "adopt a real queue immediately" is a genuinely well-calibrated middle path — it avoided both under-building (Sprint 1's direct-insert pattern, which didn't scale to multiple publishers) and over-building (a queue system with no consumer yet to justify its complexity).

**Which decisions created technical debt, plainly acknowledged rather than defended?** Forcing the whole app dynamic to fix the build failure is the most direct example — it solved the immediate problem correctly but traded away all static optimization site-wide, including for a login page that has no reason to need it, and that tradeoff wasn't interrogated at the time, just accepted under the pressure of "make the build pass." Denormalizing `organization_id` onto `mission_events` and `decisions` (ADR-007) is a deliberate, reasoned tradeoff, but it's still debt in the classic sense: a value that must now be kept in sync with its source of truth by convention rather than by a database constraint, and nothing enforces that a mission's `organization_id` can never diverge from its events' `organization_id` beyond "no code path does this today." The decision to ship `decisions` and most of `companies`' columns as write-path-free schema is defensible (avoiding guessing at a schema before the consuming system exists) but it means this sprint's two most conceptually important tables are, in practice, almost entirely inert — a future reader of this codebase who sees a fully-fleshed `companies` table with a `do_not_contact` compliance flag could very reasonably assume compliance is handled, when it isn't.

**At 10,000 users, 100 agencies, 1 million missions, and dozens of AI agents, which parts of the current implementation become bottlenecks?** In rough order of how early they'd bite: **(1) the complete absence of a job runner/queue** — this isn't a bottleneck so much as a hard blocker, since dozens of concurrent agents cannot run as inline request handlers at all; whatever gets built for Sprint 3's minimal case would need to be re-architected, not just scaled, to handle that concurrency. **(2) The in-process, non-durable event bus** — explicitly cannot survive being the coordination mechanism between independent agent workers; it would need to already be replaced with a durable transport long before agent count reaches "dozens." **(3) `mission_events` as a single unbounded, unpartitioned table** — at 1 million missions each generating multiple events, this becomes the largest table in the schema with no partitioning strategy (by `organization_id`, by time, or both) and no retention/archival policy; every RLS check on it also pays a `SECURITY DEFINER` function-call cost per row, which is correct but not free at that volume. **(4) RLS-via-function-call generally** — the standard scaling fix once this matters is moving organization membership into a JWT custom claim so RLS policies compare against the token directly rather than querying `organization_members` on every check; not done, and would be a meaningful migration once query volume justifies it. **(5) Unbounded list queries with no pagination** anywhere missions/events/decisions are fetched — `listByOrganization`/`listByMission` today, would need cursor-based pagination well before 1 million rows exist in any of these tables. **(6) The synchronous, multi-step, non-transactional `createMission()`** — at low volume, an occasional orphaned row from a partial failure is a nuisance; at high concurrent volume, it's a routine source of data integrity bugs that would need the Postgres-RPC fix described in Technical Debt.

**What would I redesign if starting over, knowing what I know now?** Three things. First, I would not leave the event bus with zero durable transport for an entire sprint — even a minimal Postgres-backed job/outbox table (agents claim a row, process it, mark it done, with basic lease/retry semantics) is cheap to build and would have closed the gap between "infrastructure exists" and "infrastructure is usable by Sprint 3" that this review had to name explicitly as the single largest limitation. Building the event bus's persistence and pub/sub halves without also building the minimal durable queue that makes it actually consumable by a background process was building half of the necessary infrastructure and declaring the seam finished. Second, I would wrap `createMission()`'s multi-step write in a single Postgres function from the start rather than sequential client-side calls — the transactional-integrity gap is exactly the kind of thing that's nearly free to get right at the beginning and meaningfully more work to retrofit once other code depends on the current multi-call shape. Third, I would have written at least a handful of unit tests for the state machine's transition logic in the same sprint that built it, not deferred testing to an indefinite future sprint for a second time in a row — the code was written in a dependency-injected, testable shape specifically to make this easy, and then nothing was done with that design property. None of these three are large redesigns; that's precisely the point being made here — they were all cheap to do correctly the first time and are now debt that has to be consciously paid down rather than having simply not existed.
